# 计算域内的原生并行编译与运行

更新：2026-10-27。

**已确认的边界：Blink 提供计算域内的原生并行编译与运行；编译域和运行域可以不同。更大系统由上层应用将这些计算分块级联。** 不以千万节点统一计算、跨域全局调度或整个超算系统的治理作为语言和执行基础的研发目标，也不据此为计算域规定武断的节点数量上限。

本文件细化架构中的计算域边界。下述职责、数据和完成关系是设计方案；示例语法、标准库接口、命令参数、产物封装和节点协议尚待语言研发落实，不能作为当前可用教程。当前能力分别见 [语言规范](BLanguage.md) 与 [Issues](Issues.md)；架构事实源仍为 [Architecture](Architecture.md#计算域内的原生编译与运行设计边界)。

## 1. Blink 负责哪一块

一次原生并行执行使用一个计算域内选定的节点和设备。域内可以有 CPU 多核、SIMD、GPU、多个设备和多台计算机；源码表达算法、数据访问、分片与协作，编译器和原生执行框架完成域内计算、通信、依赖推进及完成交接。

上层应用可以分别调用多个域中的 B 程序或库，组织它们的输入、输出和业务流程。跨域阶段顺序、数据交换、结果汇总、持久化、资源调配及故障策略属于该应用。Blink 保持完整通用语言方向，允许用户用 B 编写这样的应用；这不把上层应用的职责变成 Blink 原生并行执行框架的内置职责。

```text
上层应用：决定分块、域间数据与阶段关系
             │              │
             ▼              ▼
         运行域 A        运行域 B
         域内原生并行    域内原生并行
             │              │
             └──由上层交换结果──┘
```

运行域 A 不是运行域 B 的父调度器。一个 `target` 不合并两个独立计算域，不把跨域调用隐藏在普通函数调用或数组下标中；上层需要级联时，通过明确的应用或库接口组织。域内的分组与子集仍是同一域中的资源选择，不要求每个子任务重新建立一个域。

## 2. 计算域、数据域和 target

| 概念 | 含义 | 所有者与有效期 |
|---|---|---|
| 计算域 | 一组已加入、可授权使用并可实际通信的节点及其资源 | 域配置与节点成员关系的所有者；不随每个程序重新安装 |
| 本次参与资源 | 本次构建或执行实际取得的节点、CPU／GPU 和占用范围 | 本次构建／执行与真实资源所有者；不等于域内全部节点 |
| `target` | 对本次执行位置或参与资源的语言引用 | 执行绑定；保留目标能力和作用范围，不是网络地址字符串 |
| 数据域 | 算法处理的逻辑数据及有效范围，如一百万个粒子 | 实际数据所有者；可以在本次参与资源间分片 |
| 代码生成目标 | 操作系统、ABI、CPU 指令能力或 GPU 后端要求 | 编译产物；与在哪台机器执行编译分别确定 |

计算域是组织资源的边界，数据域是算法的数据范围，两者不能因都叫“域”而混为一谈。一个域可以服务多个作业；一个作业只消费自己的参与资源、数据与计划，不持有其他作业的状态。共享节点的真实 CPU、GPU、内存和原生进程仍由同一实际所有者管理，不因登记了不同域或作业就复制资源所有权。

## 3. 编译域和运行域独立

```text
源码与依赖
    │
    ▼
编译域 build：blc -c → 已编译目标文件 → bllink
    │
    ▼
可部署的原生产物与必要参与节点代码
    │
    ▼
运行域 simulation：本机入口 + 选定节点的原生计算
    │
    ▼
具有明确位置和完成状态的结果
```

两域可以相同、不同，或只在部分物理节点上重叠。本机编译后到域内运行、域内编译后在单机运行也都是合法组合。运行产物不依赖原编译域继续在线，运行域不需要源码、编译器或完整项目仓库。

编译器身份及选项属于构建输入；运行设备能力属于产物的适用条件。参与编译的机器不是默认的运行目标，编译节点数量也不写死运行节点数量。运行域改变时，只要已有产物覆盖其平台、ABI 和指令要求，就重新绑定资源与分片；缺少对应代码时明确报告，不能以运行时编译 B 源码或静默选择别的设备代替。

跨系统、跨架构需要对应原生产物和已实现的后端，计算域本身不提供尚未具备的跨平台代码生成。GPU 的 SPIR-V 与驱动建立管线的真实启动成本仍按平台事实处理，不能把驱动准备说成解释执行 B，也不能省略其耗时。

### 候选命令形态

以下参数尚未实现，只表达职责和使用顺序：

```powershell
blc -c particles.b --build-domain build -o particles.obj
bllink particles.obj -o particles.exe
.\particles.exe --run-domain simulation
```

第一条使用编译域执行编译，第二条在本机链接已经编译的产物，第三条选择运行域并直接启动原生应用。分布式编译不要求链接也远程执行；以后若支持在编译域中链接，仍由独立 `bllink` 执行该阶段，不把它塞回 `blc`。应用启动参数与程序自身参数的分界须由正式 CLI 定义，不能通过偷占任意用户参数落实。

这里的 `--run-domain` 是运行入口的候选资源绑定方式，不是编译器第二次执行程序。应用的其他输入、输出位置和业务选项由应用定义。普通本机编译与本机程序不要求计算域在线，不增加教学专用总入口、环境变量别名或必经包装程序。

## 4. 节点只加入一次，每个应用直接使用

节点部署域执行所需的正式基础，并加入指定域。基础负责真实节点身份、获准资源、可用原生执行环境以及必要连接；其具体安装和加入命令尚未确定，不提前编造命令。

节点加入与应用运行分开：

1. 部署时完成节点身份、域归属、授权、资源能力和实际通信配置。
2. 发起构建或运行时取得所需参与资源，绑定相应代码及数据。
3. 节点执行者按本次计划启动原生工作，完成后交还本次资源。

注册成功不代表所有节点间的数据通路已可用；运行依赖的通信能力须真实成立。域边界不等同于一张独占物理网络，也不假定所有成员拥有相同 GPU、内存或指令集。

一个节点上的构建和运行复用必要的身份、连接与原生进程所有者，不为两者建立重复的发现、安装或常驻调度体系。职责可以在同一程序内组织，不因为图上有几个方框就增加几个服务。也不依赖 Matrix 的服务、任务格式或运维协议；上层已有基础可以通过明确接口接入。

## 5. 各部分只承担必要职责

| 部分 | 负责 | 交付给下一部分 |
|---|---|---|
| `blc`／blanguage | 语言检查、模块与依赖、访问分析、分片／通信表示、优化及 CPU／GPU 代码生成 | 已编译代码、模块接口、目标要求、节点入口和可执行计划 |
| `bllink` | 符号、布局、重定位及目标平台映像组织 | 应用、库及参与节点所需的已链接原生产物 |
| blcompute 的执行所有者 | 本次参与资源、数据位置、通信、提交、依赖与完成 | 真正可用的结果、明确失败或结果尚不可确认的状态 |
| 节点执行者 | 本机原生进程、真实设备与其资源生命周期 | 本节点工作和传输的实际状态 |
| 域成员及资源配置所有者 | 节点加入、授权和所提供的资源范围 | 本次构建／执行获准使用的资源 |
| 上层应用 | 多域级联、业务数据交换、持久化及业务故障策略 | 应用所需的完整业务结果 |

域资源组织与本次执行推进分别承担不同职责，但不因此增加第二套设备、数据或进程权威。进入域内之后，逐元素计算在原生循环、SIMD 或 GPU 上完成，不为每个元素发网络调度请求。

## 6. 编译域如何工作

本次构建固定实际读取的源码、依赖接口、泛型／内联依赖、编译器、目标要求和选项。后续编辑不混入这次构建；本机未提交源码可以参与，不以 P4／Git 提交或正式软件发布作为普通编译前置。

`blc` 根据真实依赖形成可并行的工作。已经满足依赖的模块或代码生成单元可以分配给不同编译节点；依赖未成立的工作不能因有空闲机器就提前完成。独立模块、普通原生调用与必要的选择性内联是基础，不能把每个函数永久全量展开后再声称已具备可拆分构建。

节点只读取工作需要且获准取得的输入，不要求复制完整可编辑仓库或重新解析所有依赖。产物复用依据所有影响输出的实际输入，局部修改沿实际依赖重建；缓存由真实构建存储所有者持有。构建请求者拥有本次图及最终输出，节点执行者拥有本机工作进程和暂存，消费者完成后按原所有权释放。

`blc` 完成优化和代码生成，`bllink` 不重读 B 源码、不执行 B IR 优化或重新生成 CPU／GPU 代码。跨模块优化也在编译阶段形成明确产物与依赖。链接受平台映像和真实依赖约束，不能由分布式编译推导出链接可以无限并行；程序仍可按模块和库组织。

调度和记录只服务当前编译域与本次构建，不引入跨域资源市场、全网成员索引、全网构建调度器或统一超算控制中心。实际收益按冷构建、增量、传输、复用、链接和总耗时分别测量，不以机器数代替效果。

## 7. 从原生产物到域内执行

最终产物至少包含或明确引用：入口机器代码、参与节点的原生入口及代码、GPU 代码、公开接口与布局、目标要求、依赖关系和通信／分片描述。单文件嵌入还是配套文件封装另行确定；这是应用的部署组成，不增加用户必须手动操作的第二个运行器。

运行时选择一个域并申请本次资源，随后：

1. 将已编译的适用产物交给实际参与节点，已有相同产物时按其身份复用。
2. 节点执行者装载并启动生成的参与入口。应用 `main` 按入口语义执行一次，不在每台机器重新执行完整管理流程。
3. 按实际数据规模及参与资源绑定分片，节点执行已有本地计划；通信沿本次数据依赖发生。
4. 观察阶段、通信和所需结果的真实完成，将结果及相应访问权交给消费者。

原生产物本身可被复制部署，计算域内部的实际资源引用不能变成可任意复制到另一个域的本地地址。进入新运行域时建立新执行绑定，不携带原编译域或旧执行的实时资源引用。

编译器可以生成分片与通信计划，执行框架依据实际资源推进这些计划；数值循环执行已生成的 CPU 机器码或 GPU 代码，不由节点服务解释 B 源程序。现有本地 `ExecutionPlan` 是复用基础，域间资源治理不能插入每个本地算术阶段。域内多机表示应连接本地计划及必要通信边，不把整个框架改成通用远程业务任务系统。

## 8. 数据如何分片、通信和汇总

一个逻辑 dataset 可以在运行域内分片。输入可以直接分布式分配、初始化或从已有分片读取，不要求全部数据先放进入口机器内存。入口机器同样不必收回完整结果；只传回应用确实需要的部分。

| 关系 | 必须明确的语义 |
|---|---|
| 逻辑索引 | `.length` 和 `index()` 表示相应逻辑数据范围，分片不得使不同节点重复使用同一全局编号；物理分片长度与设备工作项编号另行表达 |
| 写入 | 每个输出范围具有实际写入所有者；多节点修改同一逻辑位置必须有明确协作语义 |
| 相邻分片 | 邻域算法先取得所需边界数据，再开始依赖它的计算；交换与后续访问形成真实依赖 |
| 重新分片 | 数据布局变更及传输是明确操作，旧读者和新写者沿真实完成点交接 |
| 归约 | 局部部分结果是私有中间数据，最终逻辑结果有明确所有者；归约顺序和数值许可单独定义 |
| 主机读取 | 显式传回需要的数据；远端计算结束不表示入口 CPU 已有对应字节 |
| 外部数据 | 本地裸指针、C++ 对象地址及 Rust 容器内部表示不能直接当作远端载荷；通过明确布局和借用／复制关系接入 |

本地普通下标不能偷偷变成任意远程读取。分片内访问、边界交换、集合通信及可表达的动态访问分别设计；编译器依据访问关系生成所需通信，无法据现有契约确定的关系应明确表达，不能伪造数据本地性。

跨机布局使用明确类型和表示，不假定编译器填充、字节序、指针宽度或 CPU／GPU 浮点结果天然一致。域内只有算法真实需要的通信边，不要求参与节点建立无条件全连接，也不为每个阶段强制全域同步。

## 9. 完整使用示意

下面演示一百万个粒子在一个运行域内各自移动，再汇总其横坐标。**这是新函数／target 模型的候选代码，不是当前语法或已测性能。** `domain_target()` 代表取得本次启动已选择的域资源；不在源码里写死编译域、运行域或节点地址。标准库名称和错误类型仍需正式定义。

```b
module particles;

import std.compute;
import std.parallel;
import std.io;

struct Particle {
    float3 position;
    float3 velocity;
};

void initialize(write dataset<Particle> particles) on compute {
    parallel (particle in particles) {
        particle.position = float3(0.0, 0.0, 0.0);
        particle.velocity = float3(1.0, 0.0, 0.0);
    }
}

void advance(inout dataset<Particle> particles, f32 dt) on compute {
    parallel (particle in particles) {
        particle.position =
            particle.position + particle.velocity * dt;
    }
}

result<u32, Error> main() on cpu {
    target workers = domain_target()?;
    let particles = dataset<Particle>(1000000, workers)?;
    let total = dataset<f32>(1, workers)?;

    on workers {
        initialize(particles);
        advance(particles, 0.5);
        reduce_sum(particles.position.x, total);
    }?;

    let local_total = transfer(total, here)?;
    println(local_total[0])?;
    return Ok(0);
}
```

这里没有 `program` 或手写发起许可。`parallel` 说明每份数据的工作，`on workers` 说明在哪些参与资源上组织本次计算，函数的目标、访问和协作条件仍由接口与编译器决定。该块示意同步完成，失败通过结果传播；`transfer` 显式取得入口 CPU 所需的本地数据，其具体复制／移动接口尚待确定。

若选择四台适用机器并采用等量连续分片，过程如下：

```text
main：取得 simulation 域内四台机器的参与资源
    │
    ├─节点 A：粒子 0       … 249999 ─ initialize → advance → 局部和
    ├─节点 B：粒子 250000  … 499999 ─ initialize → advance → 局部和
    ├─节点 C：粒子 500000  … 749999 ─ initialize → advance → 局部和
    └─节点 D：粒子 750000  … 999999 ─ initialize → advance → 局部和
                                                              │
                                         合并到 total 的实际所有者
                                                              │
                                         只传回一个标量 → 显示
```

每台机器内部还可采用 CPU 多核／SIMD 或适用 GPU。是否使用 GPU 取决于本次明确选择和代码要求，不假定域内全部设备同时参加。四台均分只是说明布局，不是强制节点数量或负载均衡策略。

一百万个粒子各得到 `position.x = 0.5`，所以期望总和为 `500000`。这是数学推导，尚无多机原生运行或加速比证据。速度取决于计算量、布局、设备与通信，不能因有四台机器就宣称快四倍。

## 10. 错误、完成与释放

一次执行绑定确定的接口／代码版本、参与资源、数据布局和依赖。成员变化不会在运行中悄悄改变这些关系；调整参与范围或迁移状态必须发生在明确的交接边界。代码、通信状态、CPU／GPU／远端资源保持到最后一个真实消费者完成，不能因入口返回或新版本上线而提前释放。

至少区分尚未接收、明确失败、明确完成和结果无法确认。计算完成但结果传输失败，也要保留两者的区别。错误包含实际阶段、节点／目标上下文和可定位的失败信息；部分节点完成不能代表整体成功。

等待超时、取消请求或连接断开，都不等于远端已停止，也不使相同数据立即恢复可写。停止申请新资源与已获授权工作能否继续按实际所有者及依赖确定，不再建立另一份写权限权威来模拟恢复。无法确认状态时保留未知，不自行重新执行、重复写入或改在本机运行。

首个多机版本不承诺断网或节点故障后的透明续算。需要跨域容灾、检查点、重算或业务补偿时，由上层应用明确组织；Blink 提供本次工作的实际结果、错误与资源交接语义，不静默承担应用策略。

## 11. C/C++、Rust 与上层级联

独立 B 应用直接运行。C/C++ 和 Rust 同样可以通过正式库接口使用 B 算法，显式传入执行上下文／域资源、输入及输出要求。同步与异步结果、错误映射、数据有效期和模块卸载保持可解释，不在每个 DLL 内创建一套全局运行框架。

上层应用可以同时持有运行域 A、B 的调用结果，明确决定何时向另一个域交付数据；域 A 的实时 target、设备句柄或 dataset 引用不能直接当作域 B 的有效资源。字节数据、格式和跨域传输可以由上层协议组织，目标域导入后建立自己的实际所有权。

Blink 不提供跨域全局 barrier、自动跨域事务或把多个域合并为一个隐形集群的调用语义。上层应用可以采用自己的网络、存储或调度架构，也可以用 B 实现；它组合的是具有清楚接口的计算分块。

## 12. 按可独立交付的部分推进

| 顺序 | 实际工作 | 原生交付范围 |
|---|---|---|
| 1 | 完善统一函数、访问与错误、独立模块、原生调用、编译／链接产物 | 本机实际应用及既有 C/C++、Rust 消费者保持可用 |
| 2 | 节点一次加入、资源取得、已编译节点入口与结果交接 | 两台实际机器，同一域内独立分片计算及一次全局归约，无手写应用客户端／服务器 |
| 3 | 在相同节点基础上推进域内编译、真实依赖、增量与产物复用 | 编译域与运行域使用不同资源，产物脱离编译域仍可部署运行 |
| 4 | 多阶段数据驻留、相邻交换、重新分片与域内异步 | 结果留在域内供后续阶段消费，通信及完成关系真实成立 |
| 5 | 按实际后端推进 CPU／GPU、异构平台与版本交接 | 对应真实设备和系统的原生产物、数值与生命周期证据 |

这些是工作拆分，不是要求等待整个语言完成才允许研发的统一关卡。构建与运行都先限定在各自所选计算域；跨域级联不进入语言执行框架的实现清单。复用必要编译和真实运行，不新增常驻测试、模拟全网调度或证明流程。
