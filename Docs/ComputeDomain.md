# 计算域内的原生并行编译与运行

更新：2026-10-27。

**已确认的边界：Blink 提供计算域内的原生并行编译与运行；编译域和运行域可以不同。更大系统由上层应用将这些计算分块级联。** 一次原生并行执行不扩展为千万节点统一计算，也不据此为计算域规定武断的节点数量上限。配套底座必须提供完整的远程运维、必要管理员操作和自身更新／恢复能力；正式 API／CLI 必须让上层能实际开发级联应用。机器管理规模与单次计算范围分别设计。

本文件细化架构中的计算域边界。下述职责、数据和完成关系是设计方案；示例语法、标准库接口、命令参数、产物封装和节点协议尚待语言研发落实，不能作为当前可用教程。当前能力分别见 [语言规范](BLanguage.md) 与 [Issues](Issues.md)；架构事实源仍为 [Architecture](Architecture.md#计算域内的原生编译与运行设计边界)。

## 1. Blink 负责哪一块

一次原生并行执行使用一个计算域内选定的节点和设备。域内可以有 CPU 多核、SIMD、GPU、多个设备和多台计算机；源码表达算法、数据访问、分片与协作，编译器和原生执行框架完成域内计算、通信、依赖推进及完成交接。

上层应用通过正式 SDK／CLI 分别调用多个域中的 B 程序或库，组织输入、输出和业务流程。跨域阶段顺序、数据交换、结果汇总、持久化、资源调配及业务故障策略由该应用决定；框架提供域、构建、执行、可交接结果和显式传输的机制。Blink 保持完整通用语言方向，允许用户用 B 编写这样的应用；上层负责编排不等于要求用户重写节点连接、身份、进程控制和数据传输底座。

```text
上层应用：决定分块、域间数据与阶段关系
             │              │
             ▼              ▼
         运行域 A        运行域 B
         域内原生并行    域内原生并行
             │              │
             └──由上层交换结果──┘
```

运行域 A 不是运行域 B 的父调度器。一个 `target` 不合并两个独立计算域，不把跨域调用隐藏在普通函数调用或数组下标中；上层需要级联时，通过明确的应用或库接口组织。域内的分组与子集仍是同一域中的资源选择，不要求每个子任务重新建立一个域。

## 2. 计算域、数据域和 target

| 概念 | 含义 | 所有者与有效期 |
|---|---|---|
| 计算域 | 一组已加入、可授权使用并可实际通信的节点及其资源 | 域配置与节点成员关系的所有者；不随每个程序重新安装 |
| 本次参与资源 | 本次构建或执行实际取得的节点、CPU／GPU 和占用范围 | 本次构建／执行与真实资源所有者；不等于域内全部节点 |
| `target` | 对本次执行位置或参与资源的语言引用 | 执行绑定；保留目标能力和作用范围，不是网络地址字符串 |
| 数据域 | 算法处理的逻辑数据及有效范围，如一百万个粒子 | 实际数据所有者；可以在本次参与资源间分片 |
| 代码生成目标 | 操作系统、ABI、CPU 指令能力或 GPU 后端要求 | 编译产物；与在哪台机器执行编译分别确定 |

计算域是组织资源的边界，数据域是算法的数据范围，两者不能因都叫“域”而混为一谈。一个域可以服务多个作业；一个作业只消费自己的参与资源、数据与计划，不持有其他作业的状态。共享节点的真实 CPU、GPU、内存和原生进程仍由同一实际所有者管理，不因登记了不同域或作业就复制资源所有权。

## 3. 编译域和运行域独立

```text
源码与依赖
    │
    ▼
编译域 build：blc -c → 已编译目标文件 → bllink
    │
    ▼
可部署的原生产物与必要参与节点代码
    │
    ▼
运行域 simulation：本机入口 + 选定节点的原生计算
    │
    ▼
具有明确位置和完成状态的结果
```

两域可以相同、不同，或只在部分物理节点上重叠。本机编译后到域内运行、域内编译后在单机运行也都是合法组合。运行产物不依赖原编译域继续在线，运行域不需要源码、编译器或完整项目仓库。

编译器身份及选项属于构建输入；运行设备能力属于产物的适用条件。参与编译的机器不是默认的运行目标，编译节点数量也不写死运行节点数量。运行域改变时，只要已有产物覆盖其平台、ABI 和指令要求，就重新绑定资源与分片；缺少对应代码时明确报告，不能以运行时编译 B 源码或静默选择别的设备代替。

跨系统、跨架构需要对应原生产物和已实现的后端，计算域本身不提供尚未具备的跨平台代码生成。GPU 的 SPIR-V 与驱动建立管线的真实启动成本仍按平台事实处理，不能把驱动准备说成解释执行 B，也不能省略其耗时。

### 候选命令形态

以下参数尚未实现，只表达职责和使用顺序：

```powershell
blc -c particles.b --build-domain build -o particles.obj
bllink particles.obj -o particles.exe
.\particles.exe --run-domain simulation
```

第一条使用编译域执行编译，第二条在本机链接已经编译的产物，第三条选择运行域并直接启动原生应用。分布式编译不要求链接也远程执行；以后若支持在编译域中链接，仍由独立 `bllink` 执行该阶段，不把它塞回 `blc`。应用启动参数与程序自身参数的分界须由正式 CLI 定义，不能通过偷占任意用户参数落实。

这里的 `--run-domain` 是运行入口的候选资源绑定方式，不是编译器第二次执行程序。应用的其他输入、输出位置和业务选项由应用定义。普通本机编译与本机程序不要求计算域在线，不增加教学专用总入口、环境变量别名或必经包装程序。

## 4. 节点只加入一次，每个应用直接使用

节点部署正式运维底座和所需域执行软件，并加入指定域。运维底座负责机器身份、远程控制、安装更新与本机权限；域执行基础负责计算成员关系、资源和原生工作。加入计算域不自动授予整机维护权。具体安装与加入命令尚未确定，不提前编造命令。

节点加入与应用运行分开：

1. 首次部署通过操作系统的合法管理入口建立机器维护根；安装可由组织现有批量部署设施完成，不要求每个用户逐机操作。
2. 底座安装／配置普通用户执行软件，域所有者赋予计算成员及资源范围；维护身份与计算身份分开。
3. 发起构建或运行时取得所需参与资源，绑定相应代码及数据。
4. 域执行者按本次计划启动原生工作，完成后交还本次资源；后续配置、更新、诊断与必要管理员动作由已授权底座完成。

注册成功不代表所有节点间的数据通路已可用；运行依赖的通信能力须真实成立。域边界不等同于一张独占物理网络，也不假定所有成员拥有相同 GPU、内存或指令集。

一个节点上的构建和运行复用必要的计算身份、连接与执行所有者，不为两者建立重复的发现或节点平台。运维角色独立于计算进程，计算异常不能关闭维护入口。以现有 BLAdmin／BLSupervisor 的独立维护职责和接口为复用起点，提取必要依赖并独立分发；不复制另一套同机维护权威，不依赖 Matrix 的业务中心、Node／Unit、任务格式或业务发布才能安装和恢复。现有来源不等于 Blink 已完成接入或跨平台交付。

## 5. 各部分只承担必要职责

| 部分 | 负责 | 交付给下一部分 |
|---|---|---|
| `blc`／blanguage | 语言检查、模块与依赖、访问分析、分片／通信表示、优化及 CPU／GPU 代码生成 | 已编译代码、模块接口、目标要求、节点入口和可执行计划 |
| `bllink` | 符号、布局、重定位及目标平台映像组织 | 应用、库及参与节点所需的已链接原生产物 |
| blcompute 的域／节点执行所有者 | 本次参与资源、实际 CPU／GPU 存储、数据位置、通信、提交、依赖与完成 | 真正可用的结果、明确失败或结果尚不可确认的状态 |
| BLSupervisor | 普通用户身份下的机器远程控制、受管原生进程、输出与文件操作、维护通信 | 普通用户操作的真实执行及维护结果，不解释计算任务 |
| BLAdmin | 本机特权动作、受保护安装与配置、底座激活／更新及稳定启动恢复 | 精确机器动作及实际采用事实；不向计算程序授予管理员权限 |
| 域成员及资源配置所有者 | 计算节点加入、计算授权和所提供的资源范围 | 本次构建／执行获准使用的资源，不授予整机维护权限 |
| 正式 SDK／CLI | 调用同一域、构建、执行、数据和独立维护协议，提供类型与生命周期绑定 | 可由 B、C/C++、Rust 或脚本调用的接口，不复制执行状态机 |
| 上层应用 | 多域级联、业务数据关系、持久化及业务故障策略 | 通过上述正式接口实现的应用结果与策略 |

域资源组织与本次执行推进分别承担不同职责，但不因此增加第二套设备、数据或进程权威。进入域内之后，逐元素计算在原生循环、SIMD 或 GPU 上完成，不为每个元素发网络调度请求。

## 6. 编译域如何工作

本次构建固定实际读取的源码、依赖接口、泛型／内联依赖、编译器、目标要求和选项。后续编辑不混入这次构建；本机未提交源码可以参与，不以 P4／Git 提交或正式软件发布作为普通编译前置。

`blc` 根据真实依赖形成可并行的工作。已经满足依赖的模块或代码生成单元可以分配给不同编译节点；依赖未成立的工作不能因有空闲机器就提前完成。独立模块、普通原生调用与必要的选择性内联是基础，不能把每个函数永久全量展开后再声称已具备可拆分构建。

节点只读取工作需要且获准取得的输入，不要求复制完整可编辑仓库或重新解析所有依赖。产物复用依据所有影响输出的实际输入，局部修改沿实际依赖重建；缓存由真实构建存储所有者持有。构建请求者拥有本次图及最终输出，节点执行者拥有本机工作进程和暂存，消费者完成后按原所有权释放。

`blc` 完成优化和代码生成，`bllink` 不重读 B 源码、不执行 B IR 优化或重新生成 CPU／GPU 代码。跨模块优化也在编译阶段形成明确产物与依赖。链接受平台映像和真实依赖约束，不能由分布式编译推导出链接可以无限并行；程序仍可按模块和库组织。

调度和记录只服务当前编译域与本次构建，不引入跨域资源市场、全网成员索引、全网构建调度器或统一超算控制中心。实际收益按冷构建、增量、传输、复用、链接和总耗时分别测量，不以机器数代替效果。

## 7. 从原生产物到域内执行

最终产物至少包含或明确引用：入口机器代码、参与节点的原生入口及代码、GPU 代码、公开接口与布局、目标要求、依赖关系和通信／分片描述。单文件嵌入还是配套文件封装另行确定；这是应用的部署组成，不增加用户必须手动操作的第二个运行器。

运行时选择一个域并申请本次资源，随后：

1. 将已编译的适用产物交给实际参与节点，已有相同产物时按其身份复用。
2. 节点执行者装载并启动生成的参与入口。应用 `main` 按入口语义执行一次，不在每台机器重新执行完整管理流程。
3. 按实际数据规模及参与资源绑定分片，节点执行已有本地计划；通信沿本次数据依赖发生。
4. 观察阶段、通信和所需结果的真实完成，将结果及相应访问权交给消费者。

原生产物本身可被复制部署，计算域内部的实际资源引用不能变成可任意复制到另一个域的本地地址。进入新运行域时建立新执行绑定，不携带原编译域或旧执行的实时资源引用。

编译器可以生成分片与通信计划，执行框架依据实际资源推进这些计划；数值循环执行已生成的 CPU 机器码或 GPU 代码，不由节点服务解释 B 源程序。现有本地 `ExecutionPlan` 是复用基础，域间资源治理不能插入每个本地算术阶段。域内多机表示应连接本地计划及必要通信边，不把整个框架改成通用远程业务任务系统。

## 8. 数据如何分片、通信和汇总

一个逻辑 dataset 可以在运行域内分片。输入可以直接分布式分配、初始化或从已有分片读取，不要求全部数据先放进入口机器内存。入口机器同样不必收回完整结果；只传回应用确实需要的部分。

| 关系 | 必须明确的语义 |
|---|---|
| 逻辑索引 | `.length` 和 `index()` 表示相应逻辑数据范围，分片不得使不同节点重复使用同一全局编号；物理分片长度与设备工作项编号另行表达 |
| 写入 | 每个输出范围具有实际写入所有者；多节点修改同一逻辑位置必须有明确协作语义 |
| 相邻分片 | 邻域算法先取得所需边界数据，再开始依赖它的计算；交换与后续访问形成真实依赖 |
| 重新分片 | 数据布局变更及传输是明确操作，旧读者和新写者沿真实完成点交接 |
| 归约 | 局部部分结果是私有中间数据，最终逻辑结果有明确所有者；归约顺序和数值许可单独定义 |
| 主机读取 | 显式传回需要的数据；远端计算结束不表示入口 CPU 已有对应字节 |
| 外部数据 | 本地裸指针、C++ 对象地址及 Rust 容器内部表示不能直接当作远端载荷；通过明确布局和借用／复制关系接入 |

本地普通下标不能偷偷变成任意远程读取。分片内访问、边界交换、集合通信及可表达的动态访问分别设计；编译器依据访问关系生成所需通信，无法据现有契约确定的关系应明确表达，不能伪造数据本地性。

跨机布局使用明确类型和表示，不假定编译器填充、字节序、指针宽度或 CPU／GPU 浮点结果天然一致。域内只有算法真实需要的通信边，不要求参与节点建立无条件全连接，也不为每个阶段强制全域同步。

## 9. 完整使用示意

下面演示一百万个粒子在一个运行域内各自移动，再汇总其横坐标。**这是新函数／target 模型的候选代码，不是当前语法或已测性能。** `domain_target()` 代表取得本次启动已选择的域资源；不在源码里写死编译域、运行域或节点地址。标准库名称和错误类型仍需正式定义。

```b
module particles;

import std.compute;
import std.parallel;
import std.io;

struct Particle {
    float3 position;
    float3 velocity;
};

void initialize(write dataset<Particle> particles) on compute {
    parallel (particle in particles) {
        particle.position = float3(0.0, 0.0, 0.0);
        particle.velocity = float3(1.0, 0.0, 0.0);
    }
}

void advance(inout dataset<Particle> particles, f32 dt) on compute {
    parallel (particle in particles) {
        particle.position =
            particle.position + particle.velocity * dt;
    }
}

result<u32, Error> main() on cpu {
    target workers = domain_target()?;
    let particles = dataset<Particle>(1000000, workers)?;
    let total = dataset<f32>(1, workers)?;

    on workers {
        initialize(particles);
        advance(particles, 0.5);
        reduce_sum(particles.position.x, total);
    }?;

    let local_total = transfer(total, here)?;
    println(local_total[0])?;
    return Ok(0);
}
```

这里没有 `program` 或手写发起许可。`parallel` 说明每份数据的工作，`on workers` 说明在哪些参与资源上组织本次计算，函数的目标、访问和协作条件仍由接口与编译器决定。该块示意同步完成，失败通过结果传播；`transfer` 显式取得入口 CPU 所需的本地数据，其具体复制／移动接口尚待确定。

若选择四台适用机器并采用等量连续分片，过程如下：

```text
main：取得 simulation 域内四台机器的参与资源
    │
    ├─节点 A：粒子 0       … 249999 ─ initialize → advance → 局部和
    ├─节点 B：粒子 250000  … 499999 ─ initialize → advance → 局部和
    ├─节点 C：粒子 500000  … 749999 ─ initialize → advance → 局部和
    └─节点 D：粒子 750000  … 999999 ─ initialize → advance → 局部和
                                                              │
                                         合并到 total 的实际所有者
                                                              │
                                         只传回一个标量 → 显示
```

每台机器内部还可采用 CPU 多核／SIMD 或适用 GPU。是否使用 GPU 取决于本次明确选择和代码要求，不假定域内全部设备同时参加。四台均分只是说明布局，不是强制节点数量或负载均衡策略。

一百万个粒子各得到 `position.x = 0.5`，所以期望总和为 `500000`。这是数学推导，尚无多机原生运行或加速比证据。速度取决于计算量、布局、设备与通信，不能因有四台机器就宣称快四倍。

## 10. 错误、完成与释放

一次执行绑定确定的接口／代码版本、参与资源、数据布局和依赖。成员变化不会在运行中悄悄改变这些关系；调整参与范围或迁移状态必须发生在明确的交接边界。代码、通信状态、CPU／GPU／远端资源保持到最后一个真实消费者完成，不能因入口返回或新版本上线而提前释放。

至少区分尚未接收、明确失败、明确完成和结果无法确认。计算完成但结果传输失败，也要保留两者的区别。错误包含实际阶段、节点／目标上下文和可定位的失败信息；部分节点完成不能代表整体成功。

等待超时、取消请求或连接断开，都不等于远端已停止，也不使相同数据立即恢复可写。停止申请新资源与已获授权工作能否继续按实际所有者及依赖确定，不再建立另一份写权限权威来模拟恢复。无法确认状态时保留未知，不自行重新执行、重复写入或改在本机运行。

计算执行不承诺断网或节点故障后的透明续算。需要跨域容灾、检查点、重算或业务补偿时，由上层应用明确组织；Blink 提供本次工作的实际结果、错误与资源交接语义，不静默承担应用策略。这不禁止维护底座恢复自身受管进程或应用预先授权的机器目标；底座恢复、计算重做和业务补偿是不同动作，不能互相冒充。

## 11. C/C++、Rust 与上层级联

独立 B 应用直接运行。C/C++ 和 Rust 同样可以通过正式库接口使用 B 算法，显式传入执行上下文／域资源、输入及输出要求。同步与异步结果、错误映射、数据有效期和模块卸载保持可解释，不在每个 DLL 内创建一套全局运行框架。

上层应用可以同时持有运行域 A、B 的调用结果，明确决定何时向另一个域交付数据；域 A 的实时 target、设备句柄或 dataset 引用不能直接当作域 B 的有效资源。字节数据、格式和跨域传输可以由上层协议组织，目标域导入后建立自己的实际所有权。

Blink 不提供跨域全局 barrier、自动跨域事务或把多个域合并为一个隐形集群的调用语义。上层应用可以采用自己的网络、存储或调度架构，也可以用 B 实现；它组合的是具有清楚接口的计算分块。

## 12. 机器运维底座的完整职责

本节起补齐整体框架，不以开发顺序代替架构。Supervisor、Admin 是运维职责，域执行进程是计算职责。计算进程可以退出或失效；维护面不读取其业务配置、域中心、任务数据库或 GPU 结果作为自身存活条件。

```text
维护 SDK／BLSupervisor CLI                 计算与级联 SDK／blctl
           │                                      │
           ▼                                      ▼
 BLSupervisor：普通用户维护入口          所选计算域的执行接口
     │                 │                         │
     │                 ▼                         ▼
     │          本机认证通道               节点计算进程
     │                 │                  ├─原生 CPU 工作
     ▼                 ▼                  └─GPU、传输与完成
 普通用户命令       BLAdmin：本机特权
 进程／输出／文件   安装、配置、启动与自身更新

操作系统原生启动／安装恢复设施持有底座的稳定启动根
```

维护入口和计算入口分别认证与授权，通信边不串成“每次计算先调用管理员命令”。监督者可以管理计算进程的原生生命周期，但不代替域执行者判断分片、阶段或业务成功；计算进程不承载维护通信线程。两者也不复制同一设备或进程的权威状态：监督者持有操作系统进程事实，计算执行者持有其进程内设备及计算事实。

底座必须覆盖以下能力，而不是只提供几个配置动作：

| 能力 | 必须交付的内容 |
|---|---|
| 机器身份与连接 | 本机产生并保护身份；按明确目标寻址；内外网经过认证运输；节点加入、离线与撤销可管理 |
| 远程普通执行 | 程序、参数、环境、目录和执行预算；真实普通用户令牌；完整进程树、退出码及停止 |
| 终端与输出 | 远程 shell／附着；stdout、stderr 按游标分段读取；断开附着不等于结束原执行 |
| 文件与诊断 | 按实际身份读写、分段传输、精确路径和真实错误；查询原生进程、磁盘、平台与维护状态 |
| 管理员操作 | 经已授权维护通道执行一般性的特权命令／脚本、系统配置、安装、驱动和服务动作，保留原始输入与结果 |
| 生命周期 | 开机启动、正常退出、明确停止、底座自身更新与恢复；不依赖计算中心或用户持续登录 |
| 批量管理 | 精确节点和有界集合选择、事件／游标、逐节点原始结果、版本采用与失败查询 |
| 开发接口 | 同一维护协议的库与 CLI；不要求上层自己拼接私有 HTTP 或逐机复制凭据 |

普通远程命令使用目标机器真实普通用户权限；目录参数不是沙箱。更窄的多用户隔离由操作系统身份、令牌、ACL 和实际进程／资源所有权落实，不能只检查路径前缀。计算程序与其子进程不因请求 GPU、共享存储或运行库而继承 SYSTEM／root。

维护进程的普通用户身份也不应被理解为“可让任意计算程序读取其密钥的共享账号”。承诺互不信任租户隔离时，维护身份、计算身份、进程访问和存储权限必须由实际 OS 边界分开；受信同用户部署不能冒充多租户安全隔离。域名、工作目录或环境变量本身不产生隔离。

管理员命令通过 Supervisor 的已认证维护请求交给本机 Admin；Admin 不提供外网监听，也不接受普通计算令牌直接调用。维护拥有者可授权一般性的远程管理，不要求为每个新命令重新建立功能白名单或逐机人工确认。具体改动仍绑定目标机器、调用方、请求、输入和真实 OS 权限；“拥有某域计算权”与“可修改机器”保持两种事实。

需要驱动、防火墙、服务或系统参数的环境准备，由预先授权的运维自动化经这些接口完成。计算接口报告实际缺少的环境条件，不能凭编译失败就自行扩大权限、修改任意系统设置。用户可一次配置管理身份、范围和更新策略，此后按该授权执行，不把每次提权交还用户。

首次安装仍必须经操作系统认可的管理入口建立权限，可使用组织已有的镜像、批量部署或设备管理设施。底座不能在一台从未授予安装权的机器上凭空取得管理员权限。建立后，正常安装、更新、配置与可恢复故障不要求重复登录、弹 UAC 或重新 bootstrap。

维护运输可以使用按需转发，但转发者只持有当前路由，不取得维护签名权、发布权或原执行结果。凭据与私钥由实际身份所有者持有；调用方使用正式 SDK 的身份配置，不要求用户建立逐机证书文件或在应用源码中嵌入管理员密码。

## 13. 更新底座自身，不能依赖被替换的进程

必须区分三种版本：运维底座版本、编译器／域执行软件版本、用户算法版本。三者具有独立发布与采用责任；更新算法不能顺带要求全网升级底座，更新底座也不能把在途算法换成新版本。

底座的发布与恢复路径独立于计算域。其必要组成是正式签名发布、可信读取与受保护本机安装／激活；不是要求新增三个常驻服务，也不是让每个节点自行编译更新。现有独立维护能力作为复用来源，不以 Matrix 或某个域中心在线为前置。

### 13.1 稳定启动根和可替换实现

Admin 的稳定启动与激活根由操作系统原生服务／安装恢复设施持有，机器身份、信任与已提交激活事实位于受保护位置，独立于可替换工作版本。Supervisor 的普通用户启动同样由该闭包建立。稳定根是 Admin 部署的组成，不另造一串相互守护的 Updater／UpdaterHost。

只让 Supervisor 下载覆盖自身，或让正在退出的 Admin 成为重新启动 Admin 的唯一执行者，都不满足该合同。Admin 工作版本的更换由仍存活的启动／激活所有者完成；稳定入口自身的更换必须进入操作系统的原生安装／恢复合同，并保留可启动、可验证且仍获授权的维护闭包，不能依赖已卸载版本执行收尾。

机器名、身份和信任不因普通更新重新生成；密钥轮换、授权撤销和所有权变化分别形成明确后继。受保护安装区和密钥不能放在普通工作区、算法输出或可任意清理的缓存中。

### 13.2 一次更新的实际生命周期

这是一次更新操作的状态交接，不是研发先后安排：

```text
精确更新目标与授权
    → 取得适用的签名制品
    → 在安装所有者处准备完整候选
    → 交接受影响的原生消费者
    → 由稳定启动所有者激活候选
    → 确认对应版本、身份与实际维护入口
    → 提交实际采用事实
    → 最后消费者退出后回收原版本
```

制品绑定内容身份、平台、组件依赖与维护协议，发布源地址本身不产生安装信任。节点持有验证公钥而非发布私钥；必须能处理合法信任轮换、撤销与过期元数据。不能把一个较旧制品伪装成后继发布，也不能混装互不兼容的 Admin／Supervisor 依赖。

更新目标、安装完成、进程已启动、维护入口实际可用和计算服务可用分别记录。候选失败不提交它为已采用版本，保留失败来源和现有已提交维护目标。稳定启动根恢复该现有目标时，仍不能把失败的更新报告成成功；不隐瞒错误后不断重装同一失败候选。

断电或崩溃后，启动根读取原子提交的完整激活事实和所属未完成操作，继续其明确的安装／交接状态，不根据目录名、最新文件时间或猜测 PID 选择版本。不产生第二个可写维护权威，也不重放已经接受的任意命令或计算任务。

### 13.3 更新与在途工作的关系

运维策略预先定义维护窗口、排空或明确终止权限。受影响计算节点停止接受新的独立工作，已经接受执行的必要派生工作仍可完成；其域执行所有者负责数据和任务状态。Supervisor 通过通用原生关闭合同发出交接要求、观察自己持有的进程闭包，不查询计算中心的任务数据库来判断自身能否更新。

仍被执行、传输或外部借用消费的库／代码不覆盖或卸载；不受影响的消费者保持原生实例。需要替换计算进程、GPU 驱动或重启 OS 时，影响及策略必须明确。未得到强制终止授权时，活动工作使本次更新保持等待／受阻，不暗中杀进程；已有授权允许自动完成相应维护，无须每次再问用户。

等待更新不占住独立维护读取、停止和修复入口。计算进程挂死时，已授权维护者仍可通过实际进程所有者终止它；停止事实和计算结果是否确定分别返回。底座恢复不自动重新执行其上原来的计算。

机器暂时离线时，发布可以完成，但该机器采用仍未完成。重新建立连接后查询当前获准的精确更新目标与原操作，不重放旧执行。正常版本通知和连接后的读取替代全网固定轮询；真实存活的运输连接不等于每个作业建立一套心跳。

操作系统无法启动、存储硬件失效或最后的受保护信任与启动根全部丢失，超出该机器自身的软件恢复能力，需要宿主／机房设施处理。该物理边界不能用无限叠加守护进程抹掉；普通底座部件损坏不能借此被写成要求用户重新部署的例外。

## 14. 对外 API 是正式产品能力

所有上层能力使用公开 SDK 与协议，不要求用户反向研究编译器 IR、拼接私有 JSON 或调用节点内部函数。接口按下表完整覆盖，具体函数名为候选：

| 接口面 | 代表操作 | 必须保持的关系 |
|---|---|---|
| 域与资源 | `domain_connect`、成员加入／退出／排空、资源查询、参与资源申请 | 域身份、成员授权、资源占用与维护权分别表达；查询按精确对象或有界游标 |
| 构建 | `compile_submit`、`link_submit`、构建观察／事件／结果 | 两个正式阶段各有输入与结果，构建域选择独立于代码目标和运行域 |
| 产物 | `artifact_register`、`artifact_open`、适用要求、读取与部署 | 不可变内容、接口与目标可追查；普通用户产物不因可运行而取得底座更新签名权 |
| 执行 | `run_submit`、`run_observe`、`run_wait`、`run_cancel`、事件订阅 | 接收、实际执行、终结与结果可用分开；每次工作绑定代码、参与者与输入 |
| 输出与数据 | `run_output`、`data_transfer`、`transfer_wait`、下载／释放 | 类型、布局、来源、有效期、访问和完成显式交接，不传裸指针冒充远端数据 |
| 维护 | 普通执行／附着／停止、文件、特权执行、配置、版本目标／采用／恢复 | 使用独立维护身份与原 Supervisor／Admin 合同；不借计算网关代授权限 |
| 观察 | 精确状态、错误、日志、进度、游标及事件 | 直接来自原所有者；显示或 CLI 不新建一份可改写的任务状态 |

构建服务拥有本次构建图，域执行所有者拥有本次运行关系，源和目标数据所有者分别拥有传输中的存储，节点维护所有者拥有机器动作。SDK 只持有对应引用，不把所有状态收进一个万能中心。

公开引用至少具有下列语义字段；这是合同中的必要信息，不意味着将私钥、本机指针或完整执行图复制给调用方：

| 引用 | 必要信息 |
|---|---|
| `DomainRef` | 稳定域身份、实际接口／路由、调用者身份及获准资源范围；网络地址变化不重新产生域身份 |
| `ArtifactRef` | 不可变代码与依赖内容身份、入口及输入输出接口、适用平台与指令要求；不绑定编译域在线或其节点数 |
| 请求身份 | 调用方、目标、唯一请求号及精确输入身份；用来查询同一动作，不能换输入沿用原请求号 |
| `RunRef` | 所属域、原执行所有者、运行身份、绑定代码／接口及输入版本；不能拿其他域的同名编号替代 |
| `DataRef` | 实际数据所有者、所属域、类型／布局、逻辑范围、结果版本、就绪与保留条件，以及获准导出关系 |
| `TransferRef` | 源引用与实际消费者、目标域及目标存储、表示转换、真实复制／传输完成与失败 |
| 更新目标 | 机器／范围、组件和内容版本、所需平台／协议、发布与维护授权、采用策略及精确前驱 |

这些引用不授予额外权限。域成员／授权变更约束后续接收；已接受工作的关闭与结果责任仍在原所有者。需要停止在途工作时使用明确取消／维护动作，不因后续配置变化遗失原结果或自动重放。

### 14.1 语言绑定和协议

- 提供 B 原生模块、稳定 C ABI，以及建立在同一 ABI／协议上的 C++ 和 Rust 绑定；C/C++ 与 Rust 同等支持。调用只发生在真实控制／数据交接边界，不逐元素经过 FFI 或远程 RPC。
- 本机原生库调用与远程 SDK 使用同一类型、错误及完成语义。远程合同是版本化的类型化请求／响应和数据描述，不能序列化本机指针、C++ 对象或 Rust 容器内部表示。
- 明确 ABI 布局、句柄归属、分配与释放、异步回调上下文、缓冲区借用期限以及接口版本。协议不支持时返回具体不支持，不能悄悄改用另一套语义。
- 命名、发现与凭据可由 SDK 配置或明确参数提供。管理一组域不要求存在掌握全网状态的唯一中心；每个域引用指向该域的真实接口与授权。
- CLI 可以提供可读文本及供脚本使用的结构化输出；JSON 是可选的展示格式，不是用户必须编写的并行程序或载荷协议。

### 14.2 接收、断线、取消和结果寿命

每个有副作用的请求携带可定位的请求身份。需要跨断线、进程更新继续查询和避免重做的接受事实，由相应实际所有者持久保存，不另建全局任务数据库。相同原请求身份只能查询同一次动作，不因断线重新获得执行机会，也不能靠请求编号绕过入口认证和授权。请求接收、任务执行和结果消费是三件事，不能将客户端成功发出请求作为任务成功。

客户端失去连接后，可以按原身份查询、订阅或附着；不知道是否接受时保留未知，不新建请求自动重做。异步等待不要求调用方定时轮询；事件流重连只从已消费游标继续观察，不重放动作。事件历史已不保留时，由同一所有者交付当前快照与后继游标，不伪造漏失事件。

取消是请求，终结由实际所有者确认。SDK 句柄退出可以解除客户端引用，但不能因此释放仍被 CPU／GPU／远端消费者使用的资源，也不自动取消已经接受的远程工作。可再次获取的运行／输出引用、主动释放和保留策略须明确；需要持久保留的结果由上层显式发布到相应存储，不假定所有结果永久驻内存。

运行终态区分成功、失败与已取消；同时表达结果是否可用、节点工作是否仍在关闭。因失联无法确认是观察状态，不是一个证明远端已结束的终态。部分输出仅在接口明示时可消费，不能按整体成功交给下游。

## 15. 用户如何真正开发跨域级联

上层通过 API 决定流程，框架完成有明确身份、类型和寿命的跨域数据交接。提供这些机制不等于在语言里建设全局任务调度系统。

例如域 A 处理原始点，域 B 消费 A 的点并计算统计：

```text
上层应用
  ├─在 A 提交 prepare 的原生产物 → 取得运行身份
  ├─等待 A 的 points 输出真正可用 → 保持输出引用
  ├─显式将 points 交给 B → 取得传输身份
  ├─确认 B 的数据已就绪
  ├─在 B 提交 solve，并将该数据绑定到 points 输入
  └─消费 B 的 statistics 输出
```

`DataRef` 引用源所有者持有的输出，包含类型／布局、内容或结果版本、位置范围与有效期；本身不是物理地址，也不凭字符串产生读取权。对方仍须有源端导出及目标域导入权限。传输期间源输出保持真实消费者引用，目标端使用独立拥有的存储；目标数据完整就绪后才发布为可消费输入，部分字节不能被当作成功结果。

数据可以由参与节点直接传到目标域，或按用户选择经过共享存储，不必先下载到编排机。若需跨表示转换，显式选择转换及数值许可；同名结构体不自动证明布局相同。流式交接也必须显式声明分块、消费和背压关系，不能把下例的完整结果等待偷偷改成部分流消费。

下面是候选 Rust SDK 的完整上层调用示意，**当前尚无此 SDK，不能编译运行**；同样的操作应提供 B 和 C/C++ 接口。两份 `.blpkg` 代表已编译部署产物，封装扩展名仍待定：

```rust
use blink_control::*;

fn main() -> Result<(), Error> {
    let prepare_domain = domain_connect("prepare")?;
    let solve_domain = domain_connect("solve")?;
    let prepare_code = artifact_register(&prepare_domain, "prepare.blpkg")?;
    let solve_code = artifact_register(&solve_domain, "solve.blpkg")?;

    let prepare = run_submit(
        &prepare_domain, &prepare_code, input_none()
    )?;
    run_wait(&prepare)?;
    let points = run_output(&prepare, "points")?;

    let copied_points = data_transfer(&points, &solve_domain)?;
    transfer_wait(&copied_points)?;

    let solve = run_submit(
        &solve_domain,
        &solve_code,
        input_from_transfer("points", &copied_points),
    )?;
    run_wait(&solve)?;

    let statistics = run_output(&solve, "statistics")?;
    output_download(&statistics, "statistics.bin")?;
    Ok(())
}
```

代码中的等待消费成功或明确错误，取得的数据引用以实际所有者的完成为准。Rust 绑定的局部句柄按 RAII 释放客户端引用；服务端仍持有所需在途消费者。上层程序异常退出后，已接受运行仍能按原身份查询，不凭本地析构猜测远端停止。需要接管长期编排时，上层持久化自己的运行／输出引用和业务流程；SDK 不另建全局工作流引擎。

两域独立提交，无跨域原子提交保证。如果 A 成功而 B 失败，上层可以保留 A 输出、修正 B 的条件再显式发起新工作；框架不自动重做 A。输出持久化、重算、补偿或跨域一致性策略由上层决定，接口提供所需结果与真实失败。

正式 CLI 建议命名 `blctl`，负责域与远程计算控制，不替代 `blc`、`bllink` 或直接运行 exe。命令面与 SDK 对应：`domain`、`node`、`compile`、`link`、`artifact`、`run`、`data`，有提交、观察／等待、输出和释放等明确动作；参数及语法仍待定，不提供仅供书籍使用的私有总入口。

同一条级联的候选命令如下；尖括号内容来自上一条真实返回，不是要求使用者手写 JSON，命令目前尚未实现：

```text
blctl artifact register --domain prepare prepare.blpkg
blctl artifact register --domain solve solve.blpkg
blctl run submit --domain prepare --artifact <prepare-code>
blctl run wait --domain prepare --id <prepare-run>
blctl run output --domain prepare --id <prepare-run> --name points
blctl data transfer --source <points-ref> --to-domain solve
blctl data wait --domain solve --id <points-transfer>
blctl run submit --domain solve --artifact <solve-code> --input points=<points-transfer>
blctl run wait --domain solve --id <solve-run>
blctl run output --domain solve --id <solve-run> --name statistics --to statistics.bin
```

提交返回可定位的身份，`wait` 等待同一次动作的真实结果；脚本可用 SDK 或 CLI 结构化输出接收身份，CLI 非零退出表示本条控制动作失败，不能误当成原计算已被取消。此处产物注册包含所需内容交付及接口登记，不隐式编译源码。`blctl compile`／`link` 若被上层远程调用，节点执行的仍是相应正式 `blc -c`／`bllink` 阶段，不产生另一套编译器或链接器。

维护继续使用 Supervisor 的独立 CLI／SDK，不再通过域执行接口绕一遍。现有参考源码已有 `BLSupervisor exec`、`system-exec`、`attach`、`stop`、`get`、`put` 等命令，但这只证明可复用接口存在，不能算 Blink 安装包已交付。机器管理工具可以同时使用计算与维护 SDK，分别提供对应凭据；无需用户逐机登录或手写连接和输出附着。

## 16. 大规模管理与域内计算分别兑现

配套运维底座应适应用户管理大规模机器群，甚至千万级节点；这不将一次 B 原生执行扩展到全网。管理侧按租户、域、明确机器或分区选择目标，执行侧只处理本次域内资源。单域执行者不保存全网成员、每台机器的日志或所有应用流程。

机器与域的寻址可分区，查询按精确身份或有界游标，事件按所选范围订阅；不把全量计数、全网扫描或逐节点固定轮询作为每次请求前置。通知连接的容量、当前路由和活动转发由其实际运输所有者负责，不能假定一台中心机器持有所有连接。

批量配置／发布是一组有明确范围和原始结果的机器操作；离线、失败、等待及实际采用逐节点保留，批次被接受不等于全体完成。发布目标与制品可按内容复用，节点只取自己需要的组件；发布权威不等待所有节点采用，不在每次节点连接时向全网广播。

底座提供可批量调用和观察的机制，上层选择节点分组、更新窗口、并发占用及业务级联。接口与资源所有权在设计中完整定义，规模数字仍须实际实现与测量，不能以架构文档或模拟调度声称已交付千万节点能力。

## 17. 框架完整性与实现状态

| 关系 | 架构必须完整回答的问题 |
|---|---|
| 安装 → 使用 | 谁首次建立机器权限和身份，后续如何不依赖用户重复操作 |
| 远程控制 → 特权 | 谁能修改机器，谁持有进程与结果，普通计算如何保持非提权 |
| 编译 → 运行 | 谁持有输入、产物和目标要求，为什么编译域下线不影响部署 |
| 域内 → 上层级联 | SDK 如何取得运行／输出引用、跨域交接数据及表达失败，而不要求重写节点底座 |
| 更新 → 持续维护 | 谁更新 Supervisor／Admin 自身，稳定启动根如何存活，采用与失败如何保留 |
| 关闭 → 释放 | 计算、传输、远端进程及旧版本何时真实结束，谁拥有最后的资源释放 |
| 集中视图 → 大规模节点 | 精确范围、分区、事件和逐节点事实如何取得，不把单域扩展成全网计算 |

这是一套完整设计合同，不是“先做小例子再补底座”的实施计划。精确的线格式、启动／安装格式、平台实现、稳定 ABI 字段、域授权模型及升级兼容矩阵仍须研发落实；未确定编码细节不意味着可以省略上述职责和失败交接。复用现有实际编译与原生运行，不据此新增常驻测试、审核、模拟全网或独立证明链。
